# 実データでの読み込み・遷移確認（2026-09-14）

コードの最適化はローカルに反映済みです。本番と同じ Supabase に接続した状態で、取得処理の変更前後の比較と、契約一覧・詳細の画面遷移を追加確認しました。

## データ取得処理の比較

同じログインユーザー、同じ Supabase、同じ対象データで、変更前の HEAD と変更後の TypeScript 関数を実行しました。Supabase SDK を使い、ユーザー認証と RLS を維持しています。Node 上で取得関数を実行した計測であり、ページ全体の描画時間ではありません。3 回ずつ、前後を交互に実行した中央値です。

| 対象 | 変更前 | 変更後 | 観測結果 |
|---|---:|---:|---|
| 8 処理が同時に認証・会社情報を取得 | 612 ms | 136 ms | 通信 16 回から 2 回。重複取得の削減を実データでも確認 |
| 同じ契約詳細の取得 | 306 ms | 295 ms | 差は小さく、今回のサンプルだけでは大幅改善と評価できない |
| 設定の初期取得関数 | 未計測 | 175 ms | 認証・プロフィール・会社の 3 回で完了 |

設定の旧取得関数には、招待済みプロフィールを同期する Server Action が含まれていたため、読み取り限定の今回の実 DB 比較では実行していません。以前の 15 回→3 回という設定の比較は、別途モック I/O での検証結果です。

契約一覧については、実データの取得を React Query に渡した初回が 63 ms・通信 1 回、同じキーの再取得が 1 ms 未満・通信 0 回でした。これは同じ QueryClient 内での取得関数の再利用確認です。

取得処理の計測で HTTP エラーは発生していません。データ追加・保存・削除・承認の操作は行っていません。

## 画面上での遷移確認

ローカルの開発サーバーで、次の画面を実操作で確認しました。

- 設定 → サイドメニューの「生産」 → 契約一覧。13 件の契約表示を確認。
- 契約一覧 → 契約詳細。契約番号・工期・金額・関連見積の表示を確認。
- 契約詳細 → 契約一覧 → 同じ契約詳細への再訪を 3 回確認。

| 再訪操作 | 3 回の観測値 | 中央値 |
|---|---|---:|
| 契約詳細から一覧へ戻る | 679 / 597 / 404 ms | 597 ms |
| 一覧から同じ契約詳細へ | 1187 / 784 / 1252 ms | 1187 ms |

この時間はクリック処理の開始から、実データ由来のリンクまたは見出しが表示されるまでです。ブラウザー操作ツールの待機・通信も含むため、純粋な Web Vitals 値ではありません。変更前の同じ UI 計測はなく、画面全体の改善率として比較することはできません。

開発サーバーの初回契約詳細は、待機処理の時間枠内に表示を検出できず、その後の確認で正常表示を確認しました。初回の正確な時間は取得できていないため、上の再訪値に混ぜていません。開発時の初回コンパイルも含まれるため、本番配信の初回表示速度とは区別が必要です。

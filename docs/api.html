External Integration — API & Webhook

外部連携 API・Webhook

BRIDGE のデータを他のシステムと繋ぐための設計方針と仕様をまとめたページです。kintone・Salesforce などの既存システムとの連携も、最初の設計段階から対応しています。

① What — Basics

そもそも「外部 API」と「Webhook」って何？

聞き慣れない言葉かもしれないので、まずはこの 2 つの言葉から、できるだけかみ砕いて説明します。両方とも「BRIDGE と他のシステムをつなぐパイプ」ですが、向きが逆です。

🔌 外部向け API（受け身の窓口）

「BRIDGE のデータを、外から取りに来るための窓口」です。

たとえば kintone・Salesforce・Zapier・自社の基幹システムから /api/v1/customers という URL にアクセスすると、顧客データを取得・更新できます。ブラウザを使わなくても、他のシステムが直接 BRIDGE と話せるようになります。

📣 Webhook（攻めの通知）

「BRIDGE で何かが起きたときに、自動で相手に知らせに行く仕組み」です。

たとえば「新しい顧客が登録されたら kintone に通知する」「案件のステータスが変わったら Salesforce に即時反映する」といった連携が、人の操作を介さず自動で行われます。

【外部向け API のイメージ — 相手から取りに来る】

  kintone / Salesforce                BRIDGE
  ／自社システム / Zapier              （このアプリ）
        │
        │  「顧客データをください」
        ├──────────────────────→  GET /api/v1/customers
        │                                  │
        │  ← データが返ってくる ───────────┘
        │   { "name": "田中建設", ... }

【Webhook のイメージ — こちらから知らせに行く】

  BRIDGE                          kintone / Salesforce
  （このアプリ）                    ／他システム
        │
        │  顧客が登録された！
        ├──── POST https://相手のURL ──→
        │     { event: "customer.created",
        │       data: { name: "田中建設" } }
        │                                │
        │                         受け取って自動処理 ✓
② Why — Design Policy

なぜ「最初から」設計しておく必要があるのか

「必要になってから追加すればいい」と思われがちですが、外部連携は後から付け足すと既存機能を壊しやすいタイプの機能です。先方のご要望どおり初期設計に組み込んでおく理由は、主に次の 4 つです。

論点後から追加した場合最初から設計した場合
API の URL 設計 後から /api/v1/ を追加すると、既存の画面用 URL と衝突する可能性がある 最初から /api/v1/ の形にしておくので将来の変更も安全
データの変更通知 業務ロジックのあちこちを改修して Webhook の呼び出しを差し込む必要がある 最初から「何かが変わったら知らせる」フックを組み込んでおく
API キー管理 後から専用テーブルを作ると、既存のデータ構造との整合が難しい 最初からテーブル設計に含めるので、設定画面からすぐに発行できる
囲い込みリスク API がないと「BRIDGE をやめたい」ときにデータを取り出せない API があれば、いつでも他システムに移行できる（囲い込みなし）

特に最後の「囲い込みリスク」は、先方が明確に懸念されているポイントです。API が用意されていれば、将来 BRIDGE 以外のシステムに乗り換えたくなったときも、データをエクスポートして移行する選択肢が残ります。これが ベンダーロックイン回避 の本質です。

③ How — 3 Pillars

「最初から設計する」とは、具体的に何をするのか

「外部連携前提の設計」は、思想や合言葉ではなく、初期リリースの中でやっておく具体的な作業の集まりです。中身を分解すると次の 3 つの柱になります。フェーズ 1（初期リリース）でやるのはこの 3 つです。

A

URL を最初から /api/v1/ の形にしておく

画面用の URL と API 用の URL を最初から分けておきます（例：画面は /customers、API は /api/v1/customers）。v1 が入っていることで、将来仕様が変わって v2 を作るときも既存の連携を壊さずに新旧並走できます。Stripe・kintone・Zoho など、外部公開している API はすべてこの形です。

B

「何かが起きたら通知する」フックを業務ロジックに埋め込んでおく

顧客作成・案件更新・請求発行などの処理に、「イベントを発火する仕組み」だけ最初から仕込んでおきます。フェーズ 1 ではまだ外部に通知しなくて OK。フックさえあれば、後から「kintone へ通知する」「Slack に流す」を業務ロジックを書き直さずに追加できます。これが「後から付け足すと大変」を回避する一番の肝です。

C

API キー・通知先・配信履歴のテーブルを DB に含めておく

api_keys（誰に発行したか）・webhook_endpoints（どこに通知するか）・webhook_logs（成功失敗の履歴）の 3 テーブルを最初からスキーマに含めます。Webhook 送信には HMAC 署名（Stripe と同じ方式）を付けて、受信側が「これは確かに BRIDGE から来た」と検証できるようにします。

💡 ここがポイント
この 3 つはすべて「土台」で、フェーズ 1 の時点では外部に公開する必要はありません。土台があるかないかで、フェーズ 2・3 で連携先を増やすときの工数が桁違いに変わります。先方のご要望「最初から設計しておいてほしい」の正体は、ほぼこの 3 点と言って差し支えありません。

セキュリティの考え方（柱 C の補足）

API キーは「外部システムが BRIDGE のドアを開けるための鍵」です。Zoho・kintone・Stripe と同じ仕組みで、次の 3 つを押さえます。

スコープ（権限）

「顧客は読み取りのみ」「案件は読み書き可」のように、API キーごとに操作できる範囲を絞れます。外部システムに必要最小限の権限だけ渡せます。

用途別の複数キー

「kintone 連携用」「Zapier 用」「自社スクリプト用」など、用途別にキーを発行できます。漏れたり不要になったキーはいつでも単独で無効化できます。

HMAC 署名検証

Webhook の送信には HMAC 署名を付けます。受け取る側のシステムは署名を検証することで、なりすましや改ざんを防げます（Stripe と同じ方式）。

④ Direction — One-way or Two-way

連携の方向：一方向か、双方向か

もうひとつ最初に決めておきたいのが、「データを更新できるのはどちらか」です。技術というより運用ルールの話ですが、ここの方針で設計コストが大きく変わります。

⚠ 競合（コンフリクト）について
同じ顧客データを BRIDGE と kintone の両方で同時に更新できるようにすると、「どちらが最新か」の衝突が必ず起こります。「BRIDGE を正とする」か「更新日時が新しい方を優先する」かなど、競合解決ルールを事前に合意しておくことがスムーズな実装の前提になります。
連携パターン内容実装コスト向いているケース
BRIDGE → 外部（推奨） BRIDGE を「唯一の正」とし、Webhook で外部に通知・反映する 低 ✅ BRIDGE を中心に運用する場合。最もシンプルで堅牢な設計
外部 → BRIDGE kintone / SF を正とし、変更を BRIDGE に取り込む 中 既存システムの運用を変えたくない移行期
双方向 どちらでも更新でき、自動で同期する 高 2 システムを長期並走させる場合（競合解決ルール必須）

🏆 推奨

BRIDGE を「マスターデータの正」とする BRIDGE → 外部（一方向） が、最もシンプルかつ障害が少ない設計です。Zoho・kintone も基本この発想です。将来双方向が必要になっても、この土台があれば追加対応しやすくなります。

🔄 移行期の対応

既存の kintone / SF を捨てられない移行期は、外部システムからの受信口（Inbound Webhook）を BRIDGE 側に設けることで、両方向に近い運用も実現できます。

⑤ When — Phases

いつ何をやるか — 段階的なリリース

外部連携の機能は、いきなり全部を作るのではなく段階的にリリースします。先方のご要望の核である「最初から設計しておく」はフェーズ 1 でカバーします。フェーズ 2 以降は、設定画面の操作だけで連携先を追加できる状態を目指します。

1

フェーズ 1 ― 土台設計（初期リリース同時）必須

前章の 3 つの柱（A・B・C） をすべて実装します。DB に api_keys・webhook_endpoints・webhook_logs テーブルを追加。API の URL を /api/v1/ 形式で確保。業務ロジックの各所にイベント発火フックを埋め込み。
→ この段階では外部から呼ばれなくても OK。「後で壊れない土台」を作ることが目的です。

2

フェーズ 2 ― 外部 API 公開要確認

設定画面から API キーを発行・管理できる UI をリリース。顧客・案件・見積などの外部向けエンドポイントを公開。Webhook 配信機能と、配信履歴を見られる画面を追加。
→ Zapier・n8n・自社スクリプトから BRIDGE のデータを取得・更新できる状態になります。

3

フェーズ 3 ― 個別システム連携フェーズ 2 以降

kintone・Salesforce など、具体的なシステムとの専用コネクタを実装。設定画面に kintone API トークンを入力するだけで自動同期される状態を目指します。連携方向・対象データ・競合解決ルールが合意できたものから着手します。

#確認事項なぜ必要か
① 連携したいシステムの具体名（kintone・Salesforce 以外にもあれば） 優先度をつけて実装順を決めるため
② 連携の方向（BRIDGE → 外部 / 外部 → BRIDGE / 両方向） 設計コストと方式が変わるため
③ どのデータを連携したいか（顧客・案件・請求など） API エンドポイントの優先順位を決めるため
④ リアルタイム同期か、定期バッチか リアルタイムは設計コストが高く、バッチで済むなら工数を抑えられるため
⑤ kintone：API トークンを発行できる管理者がいるか BRIDGE 側から kintone に書き込む際に、先方での発行作業が必要なため
⑥ Salesforce：Connected App の設定ができる管理者がいるか SF 側の設定作業が必要なため

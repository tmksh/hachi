External Integration — API & Webhook

外部連携 API・Webhook

BRIDGE のデータを他のシステムと繋ぐための設計方針と仕様をまとめたページです。kintone・Salesforce などの既存システムとの連携も、最初の設計段階から対応しています。

Basics

外部 API と Webhook とは？

まずこの2つの言葉を、できるだけわかりやすく説明します。

🔌 外部向け API

「BRIDGE のデータを外から取り出したり、書き込んだりするための窓口」です。

たとえば Salesforce や kintone、自社の基幹システムから /api/v1/customers という URL にアクセスすると、顧客データを取得・更新できます。ブラウザを使わなくても、他のシステムが直接 BRIDGE と話せるようになります。

📣 Webhook（ウェブフック）

「BRIDGE 内で何かが起きたとき、自動で相手のシステムに通知する仕組み」です。

たとえば「新しい顧客が登録されたら kintone に自動で通知する」「案件のステータスが変わったら Salesforce に即時反映する」ということが、ボタンを押さなくても自動で行われます。

【外部向け API のイメージ】

  kintone / Salesforce                BRIDGE
  ／自社システム / Zapier              （このアプリ）
        │
        │  「顧客データをください」
        ├──────────────────────→  GET /api/v1/customers
        │                                  │
        │  ← データが返ってくる ───────────┘
        │   { "name": "田中建設", ... }

【Webhook のイメージ】

  BRIDGE                          kintone / Salesforce
  （このアプリ）                    ／他システム
        │
        │  顧客が登録された！
        ├──── POST https://相手のURL ──→
        │     { event: "customer.created",
        │       data: { name: "田中建設" } }
        │                                │
        │                         受け取って自動処理 ✓
Design Policy

なぜ最初の設計段階から対応するのか

「後から追加すればいい」と思われがちですが、外部連携は後から付け足すと大変なことになります。理由は主に3つです。

問題後から追加した場合最初から設計した場合
APIのURL設計 後から /api/v1/ を追加すると、既存の連携が壊れる可能性がある 最初から /api/v1/ の形にしておくので将来の変更も安全
データの変更通知 業務ロジックのあちこちを改修してWebhookの呼び出しを差し込む必要がある 最初から「何かが変更されたら通知する」仕組みを組み込んでおく
APIキー管理 後から専用テーブルを作ると既存データ構造との整合が難しい 最初からテーブル設計に含めるので、設定画面からすぐに発行できる
囲い込みリスク APIがないと「BRIDGE をやめたい」ときにデータを取り出せない APIがあれば、いつでも他システムに移行できる（囲い込みなし）

Bidirectional Sync

双方向連携について

「kintone でも BRIDGE でも登録・更新できて、両方に自動で反映したい」という双方向の同期は技術的には可能です。ただし、運用ルールを先に定めることが設計の前提になります。

⚠ 競合（コンフリクト）について
同じデータを両方のシステムで同時に更新できる場合、「どちらが最新か」の衝突が起こりえます。「BRIDGE を正とする」か「更新日時が新しい方を優先する」かなど、競合解決ルールを事前に合意しておくことがスムーズな実装につながります。
連携パターン内容実装コスト向いているケース
BRIDGE → 外部（推奨） BRIDGE を「唯一の正」とし、Webhook で外部に通知・反映する 低 ✅ BRIDGE を中心に運用する場合。最もシンプルで堅牢な設計
外部 → BRIDGE kintone / SF を正とし、変更を BRIDGE に取り込む 中 既存システムの運用を変えたくない移行期
双方向 どちらでも更新でき、自動で同期する 高 2 システムを長期並走させる場合（競合解決ルール必須）

🏆 推奨アーキテクチャ

BRIDGE を「マスターデータの正」とする BRIDGE → 外部（一方向） が、最もシンプルかつ障害が少ない設計です。将来的に双方向が必要になった場合も、この土台があれば追加対応しやすくなります。

🔄 移行期の対応

既存の kintone / SF を捨てられない移行期は、外部システムからの受信口（Inbound Webhook）を BRIDGE 側に設けることで、両方向に近い運用も実現できます。

Security

API キーと権限管理

外部 API を使うためには API キーが必要です。API キーは BRIDGE の設定画面から発行・管理できます。Stripe や kintone と同じ仕組みです。

スコープ（権限）

「顧客データは読み取りのみ」「案件は読み書き可」のように、API キーごとに操作できる範囲を絞れます。外部システムに必要最小限の権限だけ渡せます。

複数キーの発行

「kintone 連携用」「Zapier 用」「自社スクリプト用」などの用途別にキーを発行できます。不要になったキーはいつでも無効化できます。

Webhook 署名検証

Webhook の送信には HMAC 署名を付けます。受け取る側のシステムは署名を検証することで、なりすましを防げます（Stripe と同じ方式です）。

Phases

実装フェーズ

外部連携の機能は段階的にリリースします。フェーズ1で「壊れない土台」を作り、フェーズ2 以降は設定画面の操作だけで連携先を追加できる状態を目指します。

1

フェーズ1 ― 土台設計（初期リリース同時）必須

DB に api_keys・webhook_endpoints・webhook_logs テーブルを追加。API の URL は最初から /api/v1/ の形式で確保。業務ロジックの各所にイベント発火フックを埋め込んでおく。
→ この段階では外部から呼ばれなくて OK。「後で壊れない土台」が目的。

2

フェーズ2 ― 外部 API 公開要確認

設定画面から API キーを発行・管理できる UI をリリース。顧客・案件・見積の外部向けエンドポイントを公開。Webhook 配信と配信履歴画面を追加。
→ Zapier・n8n・自社スクリプトから BRIDGE のデータを取得・更新できる状態。

3

フェーズ3 ― 個別システム連携フェーズ2 以降

kintone・Salesforce など具体的なシステムとのコネクタを実装。設定画面に kintone API トークンを入力するだけでデータが自動同期される状態を目指す。連携方向・対象データ・競合解決ルールを合意した上で着手。

Next Steps

今後の確認事項

フェーズ2・3 の設計を進めるにあたり、以下について教えていただけると助かります。

#確認事項なぜ必要か
① 連携したいシステムの具体名（kintone・Salesforce 以外にもあれば） 優先度をつけて実装順を決めるため
② 連携の方向（BRIDGE → 外部 / 外部 → BRIDGE / 両方向） 設計コストと方式が変わるため
③ どのデータを連携したいか（顧客・案件・請求など） API エンドポイントの優先順位を決めるため
④ リアルタイム同期か、定期バッチか リアルタイムは設計コストが高く、バッチで済むなら工数を抑えられるため
⑤ kintone：API トークンを発行できる管理者がいるか こちらが kintone に書き込む際に先方での発行作業が必要なため
⑥ Salesforce：Connected App の設定ができる管理者がいるか SF 側の設定作業が必要なため
